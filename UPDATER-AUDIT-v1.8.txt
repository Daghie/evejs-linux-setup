EveJS v0.12.6 Universal Linux Setup v1.8
Installer / Transactional Updater Design Audit
=========================================================

Scope
-----
Fresh target: EveJS v0.12.6 / EVE build 3396210.
Audited update source: EveJS v0.12.5 only.

Permanent project boundary
--------------------------
Updater functionality belongs to the Installer.
The Launcher remains runtime-only and contains no update/backup menu.

Authoritative runtime persistence
---------------------------------
v0.12.6 NON_DOCKER_SETUP_AUDIT identifies:
  _local/gameStore/gamestore.sqlite
as main Node persistence.

It separately identifies:
  externalservices/market-server/data/generated/market.sqlite
as Market persistence and warns that a market reseed replaces the same database
that contains player orders/events/history.

Therefore v1.8 never invokes a market seeder during an update.

Static/runtime split
--------------------
v1.8 preserves the complete _local namespace, including gamestore.sqlite,
images and unknown mod-owned state.

It then deletes/regenerates only:
  _local/gameStore/data
  _local/gameStore/manifest.json

using the v0.12.6 DatabaseCreator and the same EVE build 3396210 SDE.

Configuration
-------------
v0.12.5 defaults are bundled only as update-contract comparison authority.
The target files always come from the selected official v0.12.6 release.

Three-way merge rules preserve user changes while adopting new defaults/settings.
config/version.json is always target-authoritative.

Known v0.12.5 -> v0.12.6 examples:
- gameplay.combat.turretHitChanceAdditive is newly added by v0.12.6;
- server.development.playerConnectToken changes default "test" -> "";
- a user-custom token remains user-authoritative.

Certificates/client
-------------------
The source audit proved the client build and certificate tooling unchanged
between v0.12.5 and v0.12.6. Existing certificates, copied EVE client and Proton
prefix are therefore preserved for this specific audited upgrade contract.

Transactional commit
--------------------
The target version is fully staged in a sibling directory first.

The old installation becomes a full backup using same-filesystem atomic rename.
The validated staging tree is then renamed to the original path.

The update never performs an in-place source overlay against the running
installation.

Database conservation
---------------------
Before staging:
- WAL checkpoint/truncate;
- PRAGMA integrity_check;
- SHA-256.

After staging:
- PRAGMA integrity_check;
- SHA-256 must exactly match the pre-update player DB;
- SHA-256 must exactly match the pre-update Market DB.

Post-commit validation repeats these checks.

Rollback
--------
Commit errors restore the old path immediately.
Post-commit validation errors move the failed target aside and restore the old
full installation automatically.

Manual restore
--------------
The Installer lists transactional backups.
A selected backup is copied/reflinked to a staging path first.
The current installation becomes a new pre-restore safety backup.
The selected original backup is not consumed.

SteamOS
-------
v1.8 update mode first reuses the Installer's v1.6/v1.7 native toolchain
preflight and one-package SteamOS repair guard.

No:
- steamos-unminimize --dev
- base-devel repair
- containerized EveJS build
- pacman -Sy / -Syu

Launcher
--------
The included launcher is byte-identical to v1.7.
